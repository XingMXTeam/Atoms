## 1. 表层问题 vs 底层需求

| 层次 | 内容 |
|---|---|
| 你提的问题 | “做一个类似 Atoms 的 Demo” |
| 实际目标 | 48h 内交出一份提交物，让 ROOT 评审相信你是**能端到端交付的 AI Native Builder**，从而进入下一轮 |
| 评审实际看到的东西 | ① 打开链接后的**前 3–5 分钟体验** ② 说明文档（取舍和优先级） ③ GitHub 仓库（工程质量和 AI 协作痕迹） |

**结论**：要交付的是这三件套，不是 Atoms 本身。“像不像 Atoms”只是手段。

## 2. 容易把症状当根因的 4 个地方

### ① “功能越像 Atoms 越好” → 其实是**稳定的主链路 + 讲清取舍**
5 个评估维度里，完成度、可交付性看的都是稳定性。一个流畅的主链路，比 8 个半成品功能得分高。在“工程思维”这一项里，**主动不做什么**本身就会被评估。

### ② “难点是让 AI 生成代码” → 这是所有候选人都能做到的及格线
调 LLM 输出一段 HTML 塞进 iframe，1 小时就能做完，拉不开差距。真正能拉开差距的是：
- **Agent 过程可见、可控**：计划 → 步骤 → 文件变更流式展示，可以中断、追问、回滚；
- **生成结果可靠**：预览报错自动回传给 Agent 修复（生成后立刻验证）；
- **迭代是增量的**：第二轮对话改已有代码，而不是整页重新生成。

### ③ 最致命的风险不是“功能没做完”，而是**评审打开链接时它坏了**
这是最容易被低估的根因级风险：
- LLM 额度耗尽或 Key 被刷（链接是公开的，没有注册门槛）；
- Serverless 函数超时，导致长流式输出中断；
- **网络可达性**：ROOT 很可能在国内评审，如果部署在 Vercel + 直连 OpenAI/Anthropic，链接可能打不开或很慢；
- 冷启动时是空白页：评审不知道该输入什么。

→ 需要的设计：限流和单会话预算、服务端代理 Key、模型降级链、**预置示例项目（零等待就能看到结果）**、一键示例 prompt。

### ④ “无需注册”不等于“不考虑用户”
多位评审会同时用 → 需要匿名身份（deviceId）做数据隔离，同时满足“数据持久化”这条硬性要求（刷新、换标签页都不丢）。

## 3. 一个可能更值得做的切入点

你的 harness 本身就是 **planner / developer / evaluator 三角色 + rubric 否决** 的结构，和 Atoms 的 Emma(PM) / Bob(架构) / Alex(工程) 团队模式是同构的。

可以考虑把它**产品化进 Demo**：
- Atoms 里比较弱的一环是**QA / 评审 Agent**。Demo 可以加一个 “Evaluator Agent”：自动在 iframe 里跑生成的应用，抓运行时错误和白屏，按验收标准打分，不达标就打回给工程 Agent 修。
- 卖点就是 **“生成即验证”**。它和你的 harness 理念一脉相承，在文档里讲出来，故事是自洽的：我用 harness 保障自己的交付，也把同样的机制做进了产品。

这只是一个选项，要不要做取决于你的偏好（见下方提问）。

## 4. 是否使用 frontend-harness-cli

| 维度 | 评估 |
|---|---|
| 收益 | ① rubric 否决 + `fh verify` 能防止“假完成”，正好对应“完成度/稳定性” ② 仓库里的 `.harness/` 审计记录本身就是“AI Native 工程方法”的证据，加分 ③ 它是你自己的作品，可以顺带展示 |
| 成本 | 完整 clarify 链（PRD → vision → tech-design → dev-plan → acceptance）+ 每个任务精确提交 + N 次稳定通过，在 6–8h 里大约要占 **1.5–2h** |
| 风险 | 如果仓库里留下流程中途 `paused` 或评估失败的痕迹，会**反向减分**；而且评审能看出这是你自研的工具，必须走完闭环才算加分 |
| 宿主 | 本机有 `claude`/`codex`，可以用 `fh run` 无头驱动；也可以在当前环境用 `generic` 宿主手动 `fh` / `fh done` |

**初步建议**：轻量使用。只让 **1 个核心 feature（主链路）** 完整走完闭环，`fh verify`（typecheck / lint / e2e）作为全程门禁，其他 feature 不走完整流程。最终是否采用，取决于你剩余的时间。

## 5. 关键技术分岔（会直接决定 3 版方案的差异）

| 分岔 | 选项 | 影响 |
|---|---|---|
| 生成应用的形态 | 单文件 HTML（iframe srcdoc） / 多文件 React（Sandpack 或 esbuild-wasm） / WebContainer 全栈 | 复杂度依次递增；WebContainer 需要 COOP/COEP 头，还有浏览器兼容风险 |
| Agent 编排 | 单 LLM + 结构化输出 / 多角色流水线 / 工具调用循环（读写文件、执行、修复） | 决定“智能体驱动”这个卖点的深度 |
| 持久化 | localStorage / 服务端 DB + 匿名 deviceId | 后者才能做分享链接、发布这类延展能力 |
| 部署 | Vercel / Cloudflare / 国内云 | 网络可达性、流式超时限制 |
